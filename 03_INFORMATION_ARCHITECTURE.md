# DUZZA GROUP — Information architecture

## Navigation model
Primary navigation should remain concise:
- About
- Businesses (dropdown or hub)
- Work (only when verified portfolio content exists)
- Insights (only when editorial content is available)
- Contact
- Persistent primary CTA: `Request a Quote`

Within Businesses, clearly distinguish active divisions from upcoming ventures.

## Recommended routes — release one

| Route | Purpose | Status |
|---|---|---|
| `/` | Parent group landing page; route visitors to the right division | Required |
| `/about` | Group story, vision, values, leadership and verified legal details | Required; content gaps |
| `/businesses` | Overview of active and upcoming divisions | Required |
| `/projects` | Duzza Projects capabilities and enquiry routes | Required; confirm trading name |
| `/projects/services` | Engineering/construction, oil & gas, marine/survey and supply capabilities | Optional if page length warrants; can be sections initially |
| `/projects/equipment` | Equipment hire catalogue and enquiry | Only publish when inventory is supplied |
| `/branding` | Duzza Branding services, international positioning and selected work | Required |
| `/work` | Filterable verified case studies across divisions | Publish only when enough approved records exist; otherwise hide route/nav |
| `/fashion` | Coming-soon teaser | Optional; only if client wants a public teaser |
| `/food` | Bakery/restaurant coming-soon teaser | Optional; only if client wants a public teaser |
| `/insights` | News/articles | Optional; launch only with an editorial owner and real content |
| `/contact` | General and partnership enquiries | Required |
| `/contact/project-enquiry` | Project/contracting quote form | Required |
| `/contact/branding-brief` | Branding project brief form | Required |
| `/privacy` | Approved privacy notice | Required before collecting personal data |
| `/terms` | Approved terms, if applicable | Client/legal review |

Do not publish empty pages or dead-end routes. If there is insufficient verified content, keep a section off the public navigation until it is ready.

## User journeys

### Project / procurement visitor
Home → Projects → relevant capability → verified work/equipment/process → Project enquiry → confirmation.

### Equipment hire visitor
Home or Projects → Equipment → selected item and use case → prefilled equipment enquiry. Do not display availability or specifications until supplied and maintained by the client.

### Branding prospect
Home → Branding → services → selected work/case study → process → Branding brief → confirmation.

Branding should speak to an international audience. Country filters or country labels may be shown only for real, approved client/project records.

### General / partnership visitor
Home → About or Businesses → Contact → general enquiry.

### Future-division visitor
Home → Fashion/Food teaser → clear Coming soon status → optional consent-based interest capture. Do not collect an email/phone until a destination inbox, privacy wording and responsible owner are configured.

## Homepage section order
1. Header with combined logo lockup and concise navigation.
2. Hero: parent-group positioning statement, short explanation, two primary routes (`Explore our businesses`, `Request a Quote`).
3. Active businesses: Duzza Projects and Duzza Branding, visually distinct.
4. Selected work or capability highlights — only verified content. If no evidence is approved, use service/capability overview instead.
5. Why DUZZA / operating approach — factual, non-inflated copy.
6. Coming-soon ventures — optional and clearly labelled.
7. Latest insights — only if editorial content exists.
8. Closing CTA and contact routes.
9. Footer with approved legal identity, contact details, social links and privacy link.

## Page principles
- Avoid combining Projects and Branding into one generic service list.
- Keep one main action per page, with secondary actions only where useful.
- Do not force a portfolio or insights section into launch if there is no real content.
- Use a single domain and one codebase for release one. Separate microsites can be considered only when a future consumer division matures enough to justify it.
